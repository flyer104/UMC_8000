## 1. 工程全景

### 1.1 自顶向下的层次

```
UMC_8000                    ← 顶层：只做连线
├── u_datapath              ← 数据通路：执行搬运与运算
│   ├── mem_in_demux        ┐
│   ├── sum_out_demux       ├ demux（一进两出）
│   ├── sum_in_mux          ← mux（两进一出）
│   ├── sum (register)      ← 累加器 ACC
│   └── adder               ← 8 位加法器
├── u_controller            ← 控制器：指令译码
└── u_pc                    ← 程序计数器：含停机锁存
```

> 顶层实例统一用 `u_` 前缀，避免实例名与模块名同名。
> 波形里的层次路径随之变成
> `global_tb.UMC_8000.u_datapath.sum_output`。

### 1.2 文件清单

| 文件 | 职责 |
| --- | --- |
| `core/UMC-8000.v` | 顶层连线，不含逻辑 |
| `core/controller.v` | 位切片 + `case` 译码 |
| `core/datapath.v` | 实例化并连接 5 个零件 |
| `core/pc.v` | `pc + 1`，含 `halt` 锁存 |
| `core/mod/adder.v` | `assign out = a1 + a2;` |
| `core/mod/mux.v` | 含 `demux` 和 `mux` 两个模块 |
| `core/mod/reg.v` | 异步复位 + 写使能 + 保持 |

**注意**：`mux.v` 里放了两个模块（`demux` 和 `mux`），
文件名只反映了其中一个。这是刻意的（两者都只有 4 行），
但引用模块时要记住两个名字都在这个文件里。

### 1.3 端口与信号流

**顶层接口**

| 方向 | 信号 | 宽度 | 说明 |
| --- | --- | --- | --- |
| in | `clk`, `rst` | 1 | 时钟与复位 |
| in | `instru` | 8 | 从指令 ROM 取回的指令 |
| in | `mem_rdata` | 8 | 从数据内存读回的数据 |
| out | `pc` | 8 | 当前指令地址 |
| out | `mem_addr` | 6 | 数据访问地址 |
| out | `mem_wdata` | 8 | 要写入内存的数据 |
| out | `mem_write` | 1 | 内存写使能 |

**内部连线（只有 5 根）**

| 信号 | 从 → 到 | 宽度 |
| --- | --- | --- |
| `mem_in` | controller → datapath | 1 |
| `sum_in` | controller → datapath | 1 |
| `sum_out` | controller → datapath | 1 |
| `sum_en` | controller → datapath | 1 |
| `is_end` | controller → pc | 1 |

**这就是全部通信量。** 想搞懂这个工程，只要把那 4 根控制线
在数据通路里干了什么弄清楚就够了。

## 2. 构建顺序

自己从零写一遍时，建议按这个顺序，每步都能独立验证：

```
① adder.v      纯组合，最独立
② mux.v        demux + mux，纯组合
③ reg.v        第一个时序单元（累加器）
④ datapath.v   把 ①②③ 连起来 → 用 datapath_tb 验证
⑤ controller.v 纯组合译码      → 用 controller_tb 验证
⑥ pc.v         pc 计数 + 停机   → 用 pc_tb 验证
⑦ UMC-8000.v   顶层连线
⑧ comp_tb.v    controller + datapath 联调
⑨ global_tb.v  整机 + RAM + ROM
```

**为什么这个顺序**：每一步的依赖都已经验证过了，
出错时只需怀疑当前这一步。

这个项目适合**自底向上**构建（先小单元后整机），
因为单元够小、能单独测。

## 3. 各模块构建要点

### 3.1 `datapath.v` — 三个路由 + 一个使能

四个控制信号的作用点必须记牢：

| 信号 | 作用点 | 类型 |
| --- | --- | --- |
| `mem_in` | 输入 demux 的 `sel` | 数据路由 |
| `sum_in` | 输入 mux 的 `sel` | 数据路由 |
| `sum_out` | 输出 demux 的 `sel` | 数据路由 |
| `sum_en` | 累加器的 `en` | 状态更新 |

**三个路由、一个使能。** 路由可以随时变（组合逻辑），
使能只在时钟沿被采样（时序）。

**⚠️ 命名陷阱**：`mem_in=0` 表示"内存数据进累加器"，
`sum_out=0` 表示"累加器输出去内存"。
两个信号的 `0` 都对应**更常见的那条路径**。
不要凭名字猜，对着 demux 的实现看：

```verilog
assign dout0 = sel ? 0   : din;    // sel=0 → dout0 有效
assign dout1 = sel ? din : 0;      // sel=1 → dout1 有效
```

### 3.2 `controller.v` — 位切片 + 真值表

译码分两步，**没有查表、没有微码**：

```verilog
assign mem_addr = instru[7:2];   // 高 6 位 = 地址
assign opcode   = instru[1:0];   // 低 2 位 = 操作码
```

然后一个 `case` 把 2 位操作码映射成 6 位控制码：

```verilog
always @(*) begin
    case (opcode)
        2'b00   : code = 6'b0_0_1_0_0_0;   // load
        2'b01   : code = 6'b0_0_0_0_1_1;   // store
        2'b10   : code = 6'b0_1_1_1_0_0;   // add
        2'b11   : code = 6'b1_0_0_0_0_0;   // rot
        default : code = 6'b0_0_0_0_0_0;
    endcase
end
```

三个构建要点：

1. **组合逻辑用 `=`（阻塞赋值），不要用 `<=`。**
   用 `<=` 综合结果正确，但会让读者误以为 `code` 是时序信号。
2. **一定要写 `default`。** 现在 `opcode` 只有 2 位、四种取值列全了，
   缺 `default` 也不会出锁存器；但一旦扩到 3 位操作码，忘记补
   `default` 就会综合出 latch。
3. **6 位控制码的位序是任意的**，只要和 `assign {...} = code` 的顺序一致。

### 3.3 `pc.v` — 停机必须用状态锁存

**这是整个工程最容易写错的地方。**

```verilog
reg halt;

always @(posedge clk or negedge rst) begin
    if (!rst) begin
        halt <= 1'b0;
        pc   <= 8'b0000_0000;
    end else begin
        if (is_end) begin
            halt <= 1'b1;              // 锁存停机状态
        end
        if (!halt && !is_end) begin
            pc <= pc + 1;              // 停机时冻结
        end
    end
end
```

**为什么必须这样写**：`is_end` 是控制器的**组合逻辑输出**。
只要 PC 停在 `rot` 这条指令上，`instru` 就一直是 `0x03`，
`is_end` 就**一直是高电平**——它不是一个脉冲。

所以停机必须用**状态锁存**：把"已经停机"这件事记在一个 `halt` 寄存器里。

反例说明：如果用"每拍翻转"的边沿器件（例如 T 触发器）去响应 `is_end`，
因为它会持续为高，该器件会在每个时钟沿反复翻转，
产生的使能信号变成 1/2 分频，PC 只会半速前行而不是停止。

## 4. 控制信号真值表（核心）

**背下这张表，就掌握了这台 CPU 的一半。**

```verilog
assign {is_end,mem_in,sum_en,sum_in,sum_out,mem_write} = code;
```

位序（最高位在前）：

```
bit:    5        4        3        2        1        0
      is_end   mem_in   sum_en   sum_in   sum_out  mem_write
```

| opcode | 指令 | is_end | mem_in | sum_en | sum_in | sum_out | mem_write | 6 位控制码 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `00` | `load` | 0 | 0 | **1** | 0 | 0 | 0 | `001000` |
| `01` | `store` | 0 | 0 | 0 | 0 | **1** | **1** | `000011` |
| `10` | `add` | 0 | **1** | **1** | **1** | 0 | 0 | `011100` |
| `11` | `rot` | **1** | 0 | 0 | 0 | 0 | 0 | `100000` |

### 逐条读一遍

**`load`（`001000`）**：`mem_in=0` 把内存数据导向累加器输入，
`sum_in=0` 选择这条路径，`sum_en=1` 允许写入。
结果：`mem_rdata` 被抄进 ACC，内存不变。

**`store`（`000011`）**：`sum_out=1` 把 ACC 导向 `mem_wdata`，
`mem_write=1` 触发写入，`sum_en=0` 让 ACC 保持不变。

**`add`（`011100`）**：`mem_in=1` 把内存数据导向加法器，
`sum_to_adder` 提供 ACC 当前值，加法器算出结果，
`sum_in=1` 选择加法器输出，`sum_en=1` 写回 ACC。

**`rot`（`100000`）**：只有 `is_end=1`，其余全 0。
不写内存、不改 ACC，只发出停机请求。

### 发现一个冗余

对比这张表可以看出：

| 指令 | `mem_in` vs `sum_in` | `mem_write` vs `sum_out` |
| --- | --- | --- |
| load | 0 = 0 | 0 = 0 |
| store | 0 = 0 | 1 = 1 |
| add | 1 = 1 | 0 = 0 |
| rot | 0 = 0 | 0 = 0 |

**每一行都相等**，说明 `sum_in ≡ mem_in`、`sum_out ≡ mem_write`。
Yosys 综合时会自动把它们合并（可以在 `UMC_8000_synth.v` 里看到）：

```verilog
assign code = { is_end, mem_in, sum_en, mem_in, mem_write, mem_write };
```

也就是说，**理论上只需要 4 根控制线**。这是[练习 4](#10-扩展练习) 的内容。

## 5. 端到端示例：1 + 1

这是整个工程的"冒烟测试"。它由**两步**组成：
先在内存里放好两个 1，再由程序把它们相加并存到 `0x3`。

### 5.1 第一步：初始化内存

在内存地址 `0x0` 和 `0x1` 各放一个 `1`。
这一步由**测试平台**完成（不是 CPU 做的）：

```verilog
// tb/global_tb.v 里的 ram 模块
initial begin
    ram[0] <= 1;      // M[0] = 1   ← 第一个加数
    ram[1] <= 1;      // M[1] = 1   ← 第二个加数
end
```

此时内存状态：

| 地址 | 值 |
| --- | --- |
| `0x0` | `0x01` |
| `0x1` | `0x01` |
| `0x2` | 未初始化 |
| `0x3` | 未初始化 |

### 5.2 第二步：程序

四条指令，从地址 0 开始依次执行：

| 指令地址 | 汇编 | 机器码 | 计算过程 | 含义 |
| --- | --- | --- | --- | --- |
| `0x0` | `load 00` | `0x00` | `000000` + `00` | ACC ← M[0] |
| `0x1` | `add 01` | `0x06` | `000001` + `10` | ACC ← ACC + M[1] |
| `0x2` | `store 03` | `0x0D` | `000011` + `01` | **M[3] ← ACC** |
| `0x3` | `rot` | `0x03` | `000000` + `11` | 停机 |

在测试平台里的写法：

```verilog
// tb/global_tb.v 里的 instru_rom 模块
initial begin
    rom[0] <= 'h00;   // load  00
    rom[1] <= 'h06;   // add   01
    rom[2] <= 'h0d;   // store 03   <- 结果写入 M[3]
    rom[3] <= 'h03;   // rot
end
```

> ### ⚠️ 为什么是 `store 03`（`0x0D`）而不是 `store 02`（`0x09`）
>
> 因为需求是"把结果存放到 `0x3`"。
>
> 按编码规则算一遍：
>
> ```
> 目标地址 = 3        ⟹  6 位地址  000011
> 操作码 store = 01   ⟹  2 位操作码      01
> 拼起来（地址在前）       000011 01
> 补成 8 位               0000 1101  =  0x0D
> ```
>
> 作为对比，如果要存到 `0x2`：
>
> ```
> 地址 2 = 000010，拼 01  →  00001001  =  0x09
> ```
>
> **两个机器码长得像，但地址差 1。改程序时最容易在这里出错。**

### 5.3 第三步：逐拍执行过程

假设时钟每 10ns 一个周期，`rst` 在 t=10ns 拉低、t=15ns 释放。

| 拍 | `pc` | `instru` | 译码 | `mem_addr` | `mem_write` | `ACC` 变化 | 内存变化 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 复位 | 0 | — | — | — | 0 | 0 | — |
| 1 | 0 | `0x00` | `load 00` | 0 | 0 | 0 → **1** | — |
| 2 | 1 | `0x06` | `add 01` | 1 | 0 | 1 → **2** | — |
| 3 | 2 | `0x0D` | `store 03` | **3** | **1** | 2（不变） | **M[3] ← 2** |
| 4 | 3 | `0x03` | `rot` | 0 | 0 | 2（不变） | — （`is_end` 拉高） |
| 5 及以后 | **3** | `0x03` | 冻结 | 0 | 0 | 2 | **PC 停止** |

**每一拍的数据流细节**：

**第 1 拍 `load 00`**
`mem_addr = 0` → 读回 `mem_rdata = M[0] = 1`。
`mem_in=0` 把 1 送到 `mem_to_sum`；`sum_in=0` 选中它 → `sum_input = 1`；
`sum_en=1` → 时钟沿把 1 写进 ACC。

**第 2 拍 `add 01`**
`mem_addr = 1` → 读回 `mem_rdata = M[1] = 1`。
`mem_in=1` 把 1 送到 `mem_to_adder`；
`sum_out=0` 把 ACC 的当前值 1 送到 `sum_to_adder`；
加法器算 `1 + 1 = 2`；`sum_in=1` 选中加法器输出 → `sum_input = 2`；
`sum_en=1` → 时钟沿把 2 写进 ACC。

**第 3 拍 `store 03`**
`mem_addr = 3`。`sum_out=1` 把 ACC 的值 2 送到 `mem_wdata`；
`mem_write=1` → 时钟沿把 2 写进 `M[3]`。
注意 `sum_en=0`，所以 ACC 保持不变。

**第 4 拍 `rot`**
控制码 `100000`，只有 `is_end=1`。
`is_end` 送到 `pc.v` 的 `halt` 逻辑 → 时钟沿置 `halt=1` → PC 冻结。

### 5.4 最终结果

| 位置 | 值 | 说明 |
| --- | --- | --- |
| `ACC` | `2` | 累加器 |
| **`M[3]`** | **`2`** | **结果在这里** |
| `M[0]` | `1` | 未被改动 |
| `M[1]` | `1` | 未被改动 |
| `M[2]` | 未初始化 | 本程序没有访问它 |
| `pc` | `3` | 冻结在 `rot` 上 |

### 5.5 两个决定性的检查点

在波形上确认这两条，就说明整机工作正常：

1. **`pc` 停在 3 不再增长** —— 验证停机逻辑
2. **`M[3]` 最终等于 2** —— 验证取数、加法、存数整条链路

> **提示**：`M[3]` 在波形里叫 `global_tb.ram.ram[3]`。
> GTKWave 里展开 `global_tb` → `ram` → `ram` 数组即可找到。
> 如果看不到，也可以在测试平台里加一句
> `$display("M[3] = %0d", ram.ram[3]);` 打印出来。

**关键操作**：缩小到能看见前 5 个时钟周期，**一个沿一个沿地看**。

## 7. 综合：从 RTL 到门级网表

### 7.1 运行

```bash
cd rtl
yosys -l report.log -s synth.ys
```

| 参数 | 作用 |
| --- | --- |
| `-s synth.ys` | 执行综合脚本 |
| `-l report.log` | 把完整日志写入 `report.log` |

**输出两个文件**：

| 文件 | 由哪一步产生 | 内容 |
| --- | --- | --- |
| `UMC_8000_synth.v` | `synth.ys` 最后的 `write_verilog` | 综合后的门级网表 |
| `report.log` | `-l` 参数 | 完整日志：优化过程、`stat` 统计、`check` 结果、警告 |

综合完先查告警，**干净的结果应该是零告警**：

```bash
grep -i "warning\|error" report.log
```

如果看到 `Identifier ... is implicitly declared`，说明有跨模块连线
没有显式 `wire` 声明（见[第 8.1 节](#81-所有跨模块连线都要显式声明)）。

### 7.2 `synth.ys` 逐句解释

```tcl
read_verilog core/UMC-8000.v      # 读入 7 个源文件
...
hierarchy -check -top UMC_8000    # 层次检查 + 指定顶层

proc                              # always 块 → 逻辑网络
opt                               # 逻辑优化
fsm                               # 状态机提取（本设计无 FSM，空跑）
memory                            # 存储器推断（本设计无，空跑）
techmap                           # 映射到通用门（$_AND_ / $_DFF_ 等）
opt
stat                              # 打印统计信息
check                             # 一致性检查

write_verilog -noattr UMC_8000_synth.v
```

### 7.3 看什么

打开 `UMC_8000_synth.v`，找这几件事：

1. **模块层次是否保留** —— 本设计没做 flatten，
   所以能看到 `UMC_8000` → `datapath` → `adder` 的完整层次
2. **`code` 变成了什么** —— 会看到 `sum_in`/`sum_out` 被合并
   （见[第 4 节](#发现一个冗余)）
3. **加法器变成了什么** —— 一串 `$_AND_` / `$_XOR_` / `$_OR_`
4. **累加器变成了什么** —— `$_DFF_P_` 之类的触发器

### 7.4 关于工艺库

`synth.ys` **没有绑定具体工艺库**。想拿到真实的门数和面积，
需要额外的两步和一份 `.lib` 文件：

```tcl
dfflibmap -liberty /path/to/your.lib
abc -liberty /path/to/your.lib
```

本项目的目的是看清"哪些 RTL 变成了哪些门"，
而不是给出某个工艺下的面积功耗数字，所以没加这两步。

### 7.5 检查综合告警

```bash
grep -i "warning\|error" report.log
```

**本项目的目标状态是零告警。** 出现任何告警都应该先弄清楚原因，
最常见的两类是隐式线网和位宽截断，处理办法见
[第 8 节](#8-编码与测试约定)。

## 8. 编码与测试约定

这一节是这个项目的**写作规范**。改动 RTL 时请遵守，可以让
综合保持零告警、波形保持可读。

### 8.1 所有跨模块连线都要显式声明

```verilog
//controller-----------------------------------------------
wire is_end;            // 显式声明，再在实例化里连出去
```

Verilog 允许使用未声明的标识符（称为**隐式线网**），工具会自动
补一根 1 位 `wire` 并给出警告：

```
Warning: Identifier `\is_end' is implicitly declared.
```

**这条警告要当成错误处理。** 隐式线网是位宽 1 的默认推断，
一旦你以为自己连了 8 位信号，就会静默出错；严格的工具（`-Werror`、
部分商业工具）会直接拒绝编译。

**规则**：顶层和每个模块内部，跨实例的每一根连线都写 `wire`。

### 8.2 延迟和语句写在同一行

```verilog
// 推荐：一眼能看出有没有分号
#10  rst = 0;
#5   rst = 1;

// 不推荐：容易漏分号
#10
rst = 0;
```

如果 `$dumpvars(...)` 后面的分号误写成逗号，下一行会被当成
`$dumpvars` 的参数解析进去，**复位时序会完全错乱**，
而且很难从波形上看出来原因。

### 8.3 每个测试平台都声明 `timescale`

每个 `tb/*.v` 的第一行：

```verilog
`timescale 1ns/1ps
```

不声明时时间单位由工具决定，`#5` 可能被理解成 5ps 而不是 5ns。
本项目的时钟是 `always #5 clk = ~clk;`，即**周期 10ns / 100MHz**，
时间单位必须明确。

### 8.4 存储器位宽与端口一致

```verilog
reg[7:0] ram[0:63];     // 端口是 wire[7:0]，位宽必须一致
reg[7:0] rom[0:255];
```

存储器的声明宽度必须与它的读写端口一致 —— 本项目是 `reg[7:0]`。
宽度不一致时（例如端口 8 位、声明 9 位），写入会零扩展、
读出会截断高位，功能上"碰巧"能工作，但会误导读者以为数据宽度更大。

### 8.5 存储器要整体初始化

只初始化用到的那几格时，未初始化的位置读出来是 **X**。
X 会沿数据通路传染，让波形一片红，掩盖真正的问题。

```verilog
integer i;
initial begin
    for (i = 0; i < 256; i = i + 1)
        rom[i] <= 8'h00;        // 先整体填 0
    rom[0] <= 'h00;             // 再覆写程序
    rom[1] <= 'h06;
    rom[2] <= 'h0d;
    rom[3] <= 'h03;
end
```

### 8.6 组合逻辑用阻塞赋值

```verilog
always @(*) begin
    case (opcode)
        2'b00   : code = 6'b0_0_1_0_0_0;    // = 而不是 <=
        ...
        default : code = 6'b0_0_0_0_0_0;
    endcase
end
```

时序逻辑（`always @(posedge clk)`）用 `<=`，
组合逻辑（`always @(*)`）用 `=`。混用虽然常常也能综合正确，
但会让读者误判信号类型。

### 8.7 `case` 必须写 `default`

当前 `opcode` 只有 2 位、四种取值已经列全，缺 `default` 是安全的。
但一旦扩展操作码宽度，缺少 `default` 会综合出**锁存器（latch）**——
在 FPGA/ASIC 流程里这通常意味着设计错误。

**规则**：无条件的 `case` 都补上 `default`。

### 8.8 顶层实例统一用 `u_` 前缀

```verilog
datapath   u_datapath  ( ... );
controller u_controller( ... );
pc         u_pc        ( ... );
```

实例名与模块名相同时（`controller controller`）虽然合法，
但在层次路径上会出现 `UMC_8000.controller.controller` 这种读起来
很绕的写法，部分工具和波形查看器也会产生歧义。

## 9. 用波形定位问题

仿真是这个项目唯一的验证手段，**波形是主要证据**。
这一节讲怎么高效地用波形找问题。

### 9.1 从最小粒度开始

```
先跑 pc_tb / controller_tb / datapath_tb   ← 单元级
再跑 comp_tb                               ← 集成级
最后跑 global_tb                           ← 系统级
```

不要一上来就跑整机。单元级测试出问题时，涉及的范围只有一两个文件。

### 9.2 把信号变化列出来，而不是盯着一根线猜

`gtkwave` 看图形很直观，但定位问题时，**把每个信号的变化历史
列成表**往往更快。VCD 是纯文本，可以直接解析。

用下面的脚本打印所有信号的变化次数和序列，异常的信号会自己跳出来
（变化次数异常多、或者本该变的却一次没变）。

### 9.3 解析 VCD 的脚本

```python
import io
SRC = "rtl/tb/vcd/global_tb.vcd"

ids, changes, scopes, t, started = {}, {}, [], 0, False

# 第一遍：读 $var 声明，建立 id -> 层次.信号名 的映射
with io.open(SRC, encoding="utf-8", errors="replace") as fh:
    for line in fh:
        line = line.strip()
        if line.startswith("$scope"):      scopes.append(line.split()[2])
        elif line.startswith("$upscope"):  scopes.pop()
        elif line.startswith("$var"):
            p = line.split()
            ids[p[3]] = ".".join(scopes) + "::" + p[4]
        elif line.startswith("$enddefinitions"):
            started = True
            break

# 第二遍：收集每个 id 的值变化
with io.open(SRC, encoding="utf-8", errors="replace") as fh:
    for line in fh:
        line = line.strip()
        if not line or line.startswith("$"): continue
        if line[0] == "#":
            t = int(line[1:])
        elif line[0] == "b":
            sp = line.split()
            changes.setdefault(sp[1], []).append((t, sp[0][1:]))
        elif line[0] in "01xzXZ":
            changes.setdefault(line[1:], []).append((t, line[0]))

for vid, seq in changes.items():
    print(f"{ids.get(vid, vid):52} {len(seq):3} 次  {seq[:6]}")
```

### 9.4 三个实用技巧

**① 同一个 id 出现在多个作用域 ⟹ 它们是同一根网线**

VCD 里每个信号有一个 id。如果 `UMC_8000::is_end` 和
`UMC_8000.controller::is_end` 的 id 相同，说明这两个作用域
引用的是**同一根线**，即"端口确实连上了"。
这是验证模块间连接是否生效最直接的办法。

**② 注意 X 值**

未初始化的存储器或被清零前的寄存器会显示 `x`。
`x` 进入组合逻辑会传染，让下游全部变成 `x`。
看到成片的 `x`，先检查数据源有没有初始化，不要急着怀疑逻辑。

**③ 数变化次数**

变化的**次数**常常比取值更有信息量：

- 本该每拍 +1 的信号，变化次数只有一半 ⟹ 有信号在间歇性阻塞它
- 本该只变一次的信号，变了十几次 ⟹ 有信号在反复翻转

### 9.5 排查顺序

```
① rst 时序对不对？（1 → 0 → 1）
② clk 在动吗？周期对不对？
③ pc 在动吗？停在预期位置吗？
④ instru 是不是 X？（ROM 未初始化 / PC 越界）
⑤ is_end 有没有拉高？拉高后 pc 冻住了吗？
⑥ mem_write 有没有在 store 那一拍拉高？mem_addr 是几？
⑦ ACC 的变化符合预期吗？
⑧ 综合日志有没有告警？
```

## 10. 扩展练习

按难度排序。建议**一次只改一处，改完立刻跑仿真确认**。

### 练习 1 ★☆☆ 读懂波形

跑 `bash global_tb.sh`，用 GTKWave 打开，回答：

1. `ACC` 在第几纳秒从 0 变成 1？
2. `mem_write` 在哪一拍拉高？此时 `mem_addr` 是几？
3. `M[3]` 最终是多少？

### 练习 2 ★☆☆ 换个目标地址

把示例改成"把 1+1 的结果存到 `0x2`"。

1. 推出 `store 02` 的机器码
2. 改 `tb/global_tb.v` 里的 `rom[2]`
3. 跑仿真，确认 `mem_addr` 在第 3 拍变成 **2**，且 `M[2] = 2`

> 提示：`store 02` = 地址 `000010` + 操作码 `01` = `00001001` = `0x09`。

### 练习 3 ★★☆ 加自检断言

目前测试平台只打印一句"仿真结束"，没有真正的验证。
加上断言，让它自动检查结果：

```verilog
initial begin
    #115;
    if (ram.ram[3] !== 8'd2)
        $display("FAIL: M[3] = %0d, expected 2", ram.ram[3]);
    else
        $display("PASS: 1 + 1 = 2, stored at M[3]");
    $finish;
end
```

**进阶**：同时检查 `pc` 是否冻结在 3。

### 练习 4 ★★☆ 精简控制线

利用[第 4 节](#发现一个冗余)发现的冗余
（`sum_in ≡ mem_in`、`sum_out ≡ mem_write`），
把控制器输出从 6 根减到 4 根。

需要同时改三个文件：`controller.v`（输出端口 + `assign`）、
`datapath.v`（端口）、`UMC-8000.v`（连线）。

**验收**：仿真结果完全不变，且综合后的门数减少。

### 练习 5 ★★★ 加一条新指令

把操作码扩到 3 位（地址相应缩到 5 位），加一条 `sub n`：
`ACC ← ACC - M[n]`。

改动清单：

| 文件 | 改什么 |
| --- | --- |
| `controller.v` | `opcode` 改 3 位；`mem_addr` 改 `instru[7:3]`；`case` 加分支；新增 `sub_op` 控制线 |
| `mod/adder.v` | 新增减法器，或给加法器加"取反 + 进位" |
| `datapath.v` | 加一个 mux 在加/减之间选择 |
| `UMC-8000.v` | 新控制线连线 |

**思考**：地址从 6 位缩到 5 位，可寻址单元从 64 降到 32。
这个代价值得吗？为什么不干脆用变长指令？

### 练习 6 ★★★ 加跳转指令

最有价值的练习 —— 加上它，这台机器才第一次能写**循环**。

加 `jnz n`（累加器非零则跳转到 n）：

```
if (ACC != 0)  pc ← n
else           pc ← pc + 1
```

需要：

- `pc.v` 新增跳转输入 `jump_addr`、`jump_en`
- 一个"累加器是否为零"的判断（或非门）
- 控制器新增控制线
- `datapath` 把 `ACC` 暴露出来，或单独引一根 `acc_zero` 到 `pc`

做完后试试用 `jnz` 写一个"把 M[0..3] 累加求和"的循环程序。

### 练习 7 ★★★ 换工具

1. 用 **Verilator** 把设计编译成 C++ 模型，写一个 C++ 测试
2. 用 **Vivado / Quartus** 综合，对比门数和时序

### 11.1 指令编码

| 汇编 | 机器码公式 | opcode | 示例 |
| --- | --- | --- | --- |
| `load n` | `(n << 2) \| 00` | `00` | `load 00` = `0x00` |
| `store n` | `(n << 2) \| 01` | `01` | `store 03` = `0x0D` |
| `add n` | `(n << 2) \| 10` | `10` | `add 01` = `0x06` |
| `rot` | `0x03` | `11` | `rot` = `0x03` |

常用地址对照（避免算错）：

| 指令 | 地址 0 | 地址 1 | 地址 2 | 地址 3 |
| --- | --- | --- | --- | --- |
| `load n` | `0x00` | `0x04` | `0x08` | `0x0C` |
| `store n` | `0x01` | `0x05` | `0x09` | **`0x0D`** |
| `add n` | `0x02` | `0x06` | `0x0A` | `0x0E` |

### 11.2 本示例程序一览

```
内存初始化:   M[0] = 1        M[1] = 1

              rom[3] = 0x03   rot
期望结果:     ACC = 2         M[3] = 2        pc 冻结在 3
```
