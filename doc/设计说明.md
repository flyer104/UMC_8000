# UMC-8000 设计说明

> 面向**要改动这份 RTL 的人**：记录每个模块的设计意图、位宽是怎么定的、
> 有哪些取舍、以及为什么当初这样选。
>
> 想知道"怎么跑起来"，请看 [学习手册](学习手册.md)。

---

## 1. 设计目标与约束

### 1.1 目标

UMC-8000 的**唯一**目标是教学可解释性。所有设计决策都服从这一条：

> 一台 CPU 里的每一个信号，都应该能被初学者在波形上指出来，
> 并解释它为什么变。

### 1.2 由此推出的约束

| 约束 | 原因 |
| --- | --- |
| 单周期 | 避免流水线、冒险、转发等一整套复杂度 |
| 硬布线控制 | 避免微码 ROM 和微指令格式 |
| 累加器架构 | 避免寄存器堆的编号译码与 RAW 冲突处理 |
| 定长 8 位指令 | 避免变长指令的边界对齐问题 |
| 存储器外置 | 让 CPU 边界清晰，内存模型可替换 |
| 无标志位 | 避免状态码与条件执行 |
| 源文件不超过 10 个 | 一个人能在一小时内读完 |

### 1.3 明确的非目标

不做（也不打算做）的事：高性能、低功耗、可综合到特定工艺的高质量面积/时序、
跑操作系统、支持中断或异常、多核。

## 2. 位宽的推导

每个位宽都不是随便定的。

### 2.1 指令宽度 = 8 位

```
操作码位数 + 地址位数 = 指令宽度
    2      +     6     =     8
```

**操作码 2 位**：因为只有 4 条指令，`ceil(log2(4)) = 2`。
**地址 6 位**：因为演示程序只需要几十个单元，`log2(64) = 6`。
**合起来 8 位**：刚好一个字节，**没有一个比特被浪费**。

这个"刚好"是设计出来的，不是巧合 —— 先定"4 条指令 + 64 个单元"，
反过来推出指令宽度必须是 8 位。

### 2.2 数据宽度 = 8 位

与指令宽度一致，带来两个便利：

- 内存只需要一个位宽，**指令和数据同存**（冯·诺依曼结构）
- 累加器、加法器、内存数据线全部 8 位，不需要位宽转换

### 2.3 地址宽度 = 6 位

内存 64 个单元。选择理由：演示程序（4 条指令）+ 少量数据
（约 10 个单元）足够，且 `64 = 2^6` 是整齐的幂次。

### 2.4 PC 宽度 = 8 位（比地址宽 2 位）

`pc.v` 里 `pc` 是 8 位，但实际只用到 0–63。多出的 2 位是**余量**：

- 以后扩内存到 256 单元时不用改 PC 模块
- `pc + 1` 的进位不会立刻溢出

这是"留余量"而非"有功能"，所以在读代码时要留意这个不一致。

## 3. 模块设计意图

### 3.1 `core/UMC-8000.v` — 顶层

**职责**：实例化三个模块并连线，**不含任何逻辑**。

**为什么这么薄**：顶层越薄，越容易看懂数据流。整个 CPU 的模块间通信
只有 5 根内部连线（4 根控制线 + `is_end`）。

**设计选择**：存储器不放在顶层内部，而是留作端口。
好处是测试平台可以自由替换内存模型（RAM / ROM / 带延迟的模型）。

**实例命名**：顶层统一使用 `u_` 前缀 ——
`u_controller` / `u_datapath` / `u_pc`。
这样层次路径读起来清晰（`UMC_8000.u_datapath`），
也避免了实例名与模块名相同时部分工具产生的歧义。

### 3.2 `core/controller.v` — 控制器

**职责**：把 8 位指令翻译成 6 位控制码。

**实现方式**：硬布线（hardwired）。两个 `assign` 做位切片，
一个 `case` 做真值表映射。

**为什么不用微码**：微码适合指令多（几十条以上）、控制复杂的设计。
4 条指令用微码是杀鸡用牛刀，而且会引入 ROM 这个额外的黑箱，
违背"每个信号都能看见"的目标。

**6 位控制码的位序**（高位在前）：

```
bit:    5        4        3        2        1        0
      is_end   mem_in   sum_en   sum_in   sum_out  mem_write
```

这个位序是**任意**的，只是为了 `assign` 写起来整齐。
选择"`is_end` 放最高位"是为了让 `rot` 的控制码看起来像"最高位独热"：

```verilog
2'b11 : code = 6'b1_0_0_0_0_0;   // rot：只有 is_end
```

**两个编码约定**：

1. **组合逻辑用阻塞赋值 `=`。** 用 `<=` 综合结果正确，
   但会让人误以为 `code` 是时序信号。
2. **`case` 必须写 `default`。** 现在 `opcode` 只有 2 位、四种取值列全了，
   缺 `default` 也不会出锁存器；但一旦扩到 3 位操作码，
   忘记补 `default` 就会综合出 latch —— 这在 FPGA/ASIC 流程里通常是灾难。

### 3.3 `core/datapath.v` — 数据通路

**职责**：执行数据搬运和运算，**不理解指令语义**。

**四个控制信号的作用域**：

| 信号 | 作用点 | 类型 |
| --- | --- | --- |
| `mem_in` | 输入 demux 的 `sel` | 数据路由 |
| `sum_in` | 输入 mux 的 `sel` | 数据路由 |
| `sum_out` | 输出 demux 的 `sel` | 数据路由 |
| `sum_en` | 累加器的 `en` | 状态更新 |

**三个是路由，一个是使能。** 这个区分很重要：
路由信号可以随时变（组合逻辑），使能信号只在时钟沿被采样（时序）。

**为什么会用 demux 而不是 mux**：`mem_in` 和 `sum_out` 都是
"一个源、两个去向"，用 demux 表达最直观（虽然其中一个去向在多数时候悬空）。

**⚠️ 命名陷阱**：`mem_in=0` 表示"内存数据进累加器"，
`sum_out=0` 表示"累加器输出去内存"。
**两个信号的 `0` 都对应"更常见的那条路径"**。
读代码时务必对着 demux 的实现看，不要凭名字猜：

```verilog
assign dout0 = sel ? 0   : din;    // sel=0 → dout0 有效
assign dout1 = sel ? din : 0;      // sel=1 → dout1 有效
```

### 3.4 `core/pc.v` — 程序计数器

**职责**：每拍 `+1`，收到停机请求时冻结。

**停机的实现**：用一个 `halt` 寄存器把"已经停机"这个**状态**记住。

**关键约束**：`is_end` 是控制器的**组合逻辑输出**，是**电平**而不是脉冲。
只要 PC 还停在 `rot` 这条指令上，`instru` 就一直是 `0x03`，
`is_end` 就一直是高电平。

因此停机逻辑必须是**状态锁存**：

```verilog
if (is_end) halt <= 1'b1;              // 一旦请求，永久记住
if (!halt && !is_end) pc <= pc + 1;    // 停机后冻结
```

**推导**：如果改用"输入为 1 时每个时钟沿都翻转"的边沿器件
（例如 T 触发器）来响应 `is_end`，由于 `is_end` 会持续为高，
该器件会在每个时钟沿反复翻转，产生的使能信号变成 1/2 分频，
PC 只会半速前行而不会停止。

**这就是"电平信号要用状态锁存、脉冲信号才用边沿器件"的一个实例。**
写停机逻辑时先问自己：这个请求信号会自己变回 0 吗？

### 3.5 `core/mod/*` — 最小单元

刻意做得极小，每个都能一眼看完：

| 文件 | 行数 | 设计说明 |
| --- | --- | --- |
| `adder.v` | 6 | 纯组合，无进位输出（8 位自然截断） |
| `mux.v` | 16 | 三目运算符实现，含 `mux` 和 `demux` 两个模块 |
| `reg.v` | 15 | 异步复位 + 写使能 + 保持 |

**注意 `mux.v` 里放了两个模块**。这违反"一个文件一个模块"的常见约定，
但因为两者都只有 4 行，放在一起反而更好读。
文件名 `mux.v` 与实际内容的对应关系需要留意。

**所有时序单元都使用异步复位**：

```verilog
always @(posedge clk or negedge rst)
```

**为什么异步**：复位可以不等时钟立即生效，仿真时行为更直观。
**代价**：异步复位在真实 ASIC 流程里需要额外的复位树和时序约束。
如果要做产品级设计，通常改成同步复位。

## 4. 控制流分析

### 4.1 为什么不存在冒险

**冒险（hazard）** 只在多条指令重叠执行时才会出现。
UMC-8000 是单周期、每拍只执行一条指令的**完全顺序**模型，因此：

| 冒险类型 | 是否可能出现 | 原因 |
| --- | --- | --- |
| 结构冒险 | 否 | 每拍只有一个模块在动 |
| 数据冒险 | 否 | 没有重叠，前一条已在上一拍写完 |
| 控制冒险 | 否 | 唯一的控制转移是停机，且不需要预测 |

这是单周期设计最大的好处：**整个"冒险处理"章节可以不存在**。

### 4.2 时钟周期下界

单周期 CPU 的时钟周期必须 ≥ 最长组合逻辑路径延迟。本设计中最长路径大致是：

```
ROM 读 → 控制器译码（case）→ datapath mux → 加法器 → 累加器建立时间
```

估算：ROM 访问 + 几级门 + 8 位加法器进位链。
在典型 FPGA 上是几十纳秒量级，所以主频大概在几十 MHz。

**这就是单周期的代价**：每一拍都要等最慢的那条路，
哪怕这一拍只是在做 `load`（根本没用到加法器）。

### 4.3 关键路径的优化空间

如果要提高主频（而不是改成流水线），可以：

1. **缩短加法器进位链** —— 改成超前进位（carry-lookahead）
2. **把 `case` 译码改成一级与或** —— 减小译码延迟
3. **寄存器输出** —— 让控制信号提前一拍准备好（引入时序复杂度）

这些都是很好的进阶练习。

## 5. 控制信号的冗余

对比[学习手册第 4 节](学习手册.md#4-控制信号真值表核心)的真值表：

| 指令 | `mem_in` | `sum_in` | `mem_write` | `sum_out` |
| --- | --- | --- | --- | --- |
| load | 0 | 0 | 0 | 0 |
| store | 0 | 0 | 1 | 1 |
| add | 1 | 1 | 0 | 0 |
| rot | 0 | 0 | 0 | 0 |

**每一行都相等**，所以：

```
sum_in  ≡ mem_in
sum_out ≡ mem_write
```

Yosys 综合时会自动发现并合并（见 `UMC_8000_synth.v`）：

```verilog
// 源码
assign {is_end,mem_in,sum_en,sum_in,sum_out,mem_write} = code;

// 综合后（Yosys 化简）
assign code = { is_end, mem_in, sum_en, mem_in, mem_write, mem_write };
```

**结论**：理论上只需要 4 根控制线（`is_end`、`mem_in`、`sum_en`、`mem_write`）
就能完成全部功能。

**为什么没有改**：6 根控制线更贴合数据通路的物理结构
（每个 mux/demux 各有一根 `sel`），读代码时更直观。
但这是一个很好的重构练习，见[学习手册练习 4](学习手册.md#10-扩展练习)。

## 6. 机器码的推算与校验

### 6.1 推算规则

指令只有两个字段，机器码由地址和操作码拼接而成：

```
机器码 = (n << 2) | opcode
```

以本项目 1+1 示例的第三条指令为例（`store 03`）：

```
目标地址 = 3        ⟹  6 位地址  000011
操作码 store = 01   ⟹  2 位操作码      01
拼起来（地址在前）       000011 01
补成 8 位               0000 1101  =  0x0D
```

### 6.2 反推校验

手写机器码后，务必用反推验证一遍：

```
n  = (机器码 >> 2) & 0x3F
op = 机器码 & 0x03
```

### 6.3 容易混淆的一组值

`store 02` 与 `store 03` **只差一位地址**，机器码看起来很接近：

| 指令 | 地址字段 | 操作码 | 机器码 |
| --- | --- | --- | --- |
| `store 02` | `000010` | `01` | `0x09` |
| `store 03` | `000011` | `01` | `0x0D` |

本项目的示例是**把结果存到 `0x3`**，因此使用 `0x0D`，
汇编标注也应写作 `store 03`。

汇编助记和机器码必须**成对检查**，详见
[README 的 1+1 示例](../README.md#完整的-1--1-示例)。

## 7. 设计决策速查

| 决策 | 选择 | 被放弃的替代方案 | 理由 |
| --- | --- | --- | --- |
| 控制方式 | 硬布线 | 微码 ROM | 4 条指令不值得引入 ROM 黑箱 |
| 寄存器组织 | 累加器 | 寄存器堆 | 避免编号译码与 RAW 冲突 |
| 执行模式 | 单周期 | 多级流水 | 避免冒险处理整章复杂度 |
| 指令格式 | 8 位定长 | 变长 | 避免对齐状态机 |
| 停机实现 | `halt` 状态锁存 | 边沿器件翻转 | `is_end` 是电平信号，必须锁存 |
| 复位方式 | 异步 | 同步 | 仿真直观；代价是 ASIC 需额外约束 |
| 存储器 | 外置端口 | 内嵌 RAM | CPU 边界清晰，内存可替换 |
| 地址位序 | 高 6 位地址、低 2 位操作码 | 反过来 | 译码只需两条 `assign`；`<<2` 便于手算 |
| 控制线数量 | 6 根 | 精简到 4 根 | 贴合数据通路结构，可读性优先 |
| 综合目标 | 通用门级 | 指定工艺库 | 聚焦"逻辑变成了什么"而非流程 |

## 8. 代码约束与已知取舍

### 8.1 功能性约束

| 约束 | 后果 |
| --- | --- |
| 只有 4 条指令 | 写不了条件分支、循环、比较 |
| 没有标志位 | 无法判断"结果是否为零/进位" |
| 只有 1 个寄存器 | 中间结果只能存回内存 |
| 没有间接寻址 | 地址必须硬编码在指令里 |
| 无符号运算 | `add` 溢出按 8 位回绕（`255 + 1 = 0`） |
| `rot` 不可恢复 | 停机即结束，只能靠复位 |
| 指令与数据同存 | `store` 可以覆盖自己的代码 |

**能写的程序形态**：直线代码（straight-line code），
一条接一条执行到 `rot` 为止。

## 9. 演进路线

```
UMC-8000（现在这里）
   │  ① 加跳转指令（jnz / jmp）→ 能写循环
   ▼
带分支的程序流
   │  ② 加更多算术（sub / and / or / xor），操作码扩到 3 位
   ▼
更完整的 ALU
   │  ③ 从累加器改成寄存器堆（4 个寄存器）
   ▼
寄存器-寄存器架构
   │  ④ 拆成 2–3 级流水线，处理冒险与转发
   ▼
真正的流水线
   │  ⑤ 加指令 Cache、加中断、加特权级
   ▼
      终于接近 RISC-V 的复杂度
```

**推荐的第一个扩展**：加 `jnz`（非零跳转）。
加上它之后，这台机器才第一次能跑**循环**——那是质的飞跃。

需要改动：

| 文件 | 改什么 |
| --- | --- |
| `pc.v` | 新增 `jump_addr`、`jump_en` 输入，加一个 mux 选择下一拍 PC |
| `datapath.v` | 暴露"累加器是否为零"（一个或非门） |
| `controller.v` | 操作码扩位，`case` 加分支，新增跳转控制线 |
| `UMC-8000.v` | 新连线 |

**这个设计为什么排在最前面**：因为它是"控制流"的起点。
有了跳转，CPU 才从"计算器"变成"计算机"。
